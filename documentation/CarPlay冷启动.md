# CarPlay 冷启动连接

## 启动顺序

系统允许 DiPlay 进程启动后，`DiPlayBootInitProvider` 在 Activity 与开机广播接收器前发起准备。保留熄屏状态订阅，将蓝牙预连接、Wi-Fi 预热、本地认证准备和缓存会话准备放在音频路由、示宽灯与页面构建之前；各自使用后台工作线程。

普通 APK 不能保证进入系统启动的“第一队列”。现有开机广播优先级为 1000，Provider 的 `initOrder` 仅决定本进程中的初始化顺序。真正提前系统调度需要车机固件提供自启动或预装支持，应用侧不能保证。没有增加锁屏启动广播：当前设置和认证输入仍使用正常用户存储。

## 连接与页面

- 有有效显示参数缓存时，无需 Activity 测量，后台会话直接使用上次协商的显示配置。首页后续接管同一控制器，不重复连接。
- 已选手机触发蓝牙连接广播且用户开启对应自动连接选项时，先尝试后台会话，再展示首页；此入口不依赖“开机启动”开关。
- 自动启动中的首次本地认证准备放在后台，避免首页等待认证初始化锁。完成后重新检查自动连接、设备选择、熄屏及手动断开状态。
- 控制器先启动认证，再注册媒体与方向盘接口；视频安全策略仍在控制器启动前注册。
- 没有有效缓存、权限不满足或采用手动热点时，保留原有配置和权限流程，不臆造显示参数。

## 缓存边界

蓝牙仅预连接已选且已配对的设备，已建立的 RFCOMM socket 只移交一次，失败保留控制器原有重试路径。已有配对记录载入内存时不再重复触发持久化写入；新配对仍正常保存。

显示缓存继续校验设备身份、固件、显示/协议配置及相关权限。路口卡片主题、透明度和位置等本地外观调整不再导致缓存失效；仪表流尺寸、比例、启用状态及主屏配置改变仍会使旧缓存失效。不会缓存或复用一次性认证挑战，也不会跳过 CarPlay 认证。

## 验证速度

启用诊断日志后，比较同一车机冷启动的 `process-ready`、`bluetooth-preconnect-started`、`bluetooth-connected`、`controller-started`、`session-active` 与 `first-video-frame` 时间。区分缓存命中、首次配置、手机蓝牙未就绪三种情况；关闭诊断时不写这些日志。

本次软件测试覆盖后台启动、取消和熄屏保护、重复触发、socket 移交与缓存失效。尚未实车测量，不能据单元测试推断节省的秒数或保证连接稳定性。
